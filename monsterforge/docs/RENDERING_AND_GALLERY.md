# Rendering & Gallery — From Domain Object to Printable Card

A case study in turning a `MoveCard` domain object into an actual visual
artifact, and in showing that pipeline's real output rather than a
hand-picked demo. This document explains what the rendering layer and
its gallery demonstrate about the project's engineering approach, not
just that they work — see [PROJECT_STATUS.md](./PROJECT_STATUS.md) for
current numbers.

**See it live:** <https://alteredlilac.github.io/MonsterForge/>

## What it is

Two related pieces:

```
MoveCard → serialization.card_to_json() → rendering.render_move_card_html()
  → a printable HTML/CSS card
```

```
64 real pipeline runs (raw attack → semantic classification → domain
conversion) → one browsable gallery page, each entry opening a
drill-down into its raw input, classification, JSON, and rendered card
```

The first turns a single card into a visual artifact. The second turns
every card the project has actually produced against the real LLM API
into something a reader can click through, not just read about.

## What it demonstrates

**A single shared serialization stage, not two parallel conversions.**
A printed card has a fixed physical footprint (Magic-style, ~63×88mm) —
there's no room to print another card's full contents inside the card
that references it. That constraint, not a network-payload concern, is
why rendering consumes the same `card_to_json()` output the future API
will return rather than walking the domain model independently: a
referenced card (e.g. a linked "Trip" effect) reduces to its name and id
in both places, for the same underlying reason. See
[PIPELINE_ARCHITECTURE.md](./PIPELINE_ARCHITECTURE.md)'s discussion of
why `serialization/` is one stage shared downstream, not a fork.

**One template fragment, reused everywhere a card appears.** The
standalone single-card page and the many-card gallery render through the
exact same card markup and the exact same context-building function, not
two implementations that happen to look similar. A change to how a card
looks is a change made once, and the two views can't quietly drift apart
from each other.

**A fixed-size card, not one that grows around its content.** Every
section of the card — header, artwork, effect/bonus columns,
description — has a deterministic height regardless of what's in it.
Free text (the LLM-generated description, in particular) is capped
rather than allowed to stretch the card, the same physical-space
reasoning that governs the card's shared serialization stage above: a
real printed card doesn't resize itself to fit an unusually long
sentence.

**A rendering constraint fed back into where it originates, not just
absorbed downstream.** Once the description box's real character budget
was known from the fixed layout above, that number became an explicit
instruction in the classification prompt (capped at 160 characters)
instead of staying a silent truncation risk the renderer alone had to
handle. Verified against a second, independent run of the real API
across all 65 sample cases: the longest description came in at 143
characters, none over the limit.

**The gallery shows real pipeline output, not staged examples.** Every
one of its 64 entries comes from the same real-API sample file used
elsewhere in this project — the raw attack notation, the LLM's
classification (including its confidence and rationale), and the final
card are all what the pipeline actually produced, not hand-written
fixtures assembled to look good in a demo.

## Verified against the real pipeline

Both the individual card renderer and the gallery are exercised against
real, committed pipeline output rather than synthetic examples — see
[PROJECT_STATUS.md](./PROJECT_STATUS.md) for current test counts. The
160-character description constraint specifically was checked by running
the full 65-case sample set against the live API twice — once before the
constraint existed, once after — and comparing the resulting description
lengths, not assumed to work from reading the prompt alone.

## What's deliberately out of scope

Rendering for `CreatureCard`/`ItemCard` (only `MoveCard` is rendered so
far) and any server or web layer for the gallery itself (it's a static
file generated by a script, not served dynamically).

The gallery isn't meant to be a print workflow — it's a showcase to
browse, and doesn't offer printing at all. The standalone card page
(what `render_move_card_html()` produces, e.g. via
`render_sample_cards.py`) and the web UI (`ui/`) both print at the
card's real ~63×88mm size — verified in a real browser, not just
designed on paper — and are the actual way to get a physical card out
of this project today.
